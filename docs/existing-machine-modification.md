# 既存機体の改造とサトウキビ試作

目的は、人間が作った停止中のピストン機体へ、通常MCPの観測・差分案・
プレビュー・適用・読戻し・条件付き取消を通して部品を追加できるようにすること。
今回の基準例は、6ブロックの機体へスライムとガラスを1個ずつ追加する収穫バー。
直接の管理コマンドによる試作結果は、通常MCPや収穫動作の合格証拠に昇格させない。
作業ブランチは `codex/existing-machine-edit`。

現行の座標指定読取りは視線に依存しません。大きな差分は[区画ジョブ](large-circuit-regions.md)へ接続できます。以下の視線・上限の記述と計測は、この初期実装時点の記録です。

## 作業順序と完了条件

| 順序 | 作業 | 完了条件 |
| --- | --- | --- |
| 1 | 追加先を含む作業領域を観測 | 視線で対象を確かめ、指定した領域の空気・機体・周辺を完全取得し、不変の観測IDで後続処理へ接続 |
| 2 | 共通runtimeによる差分施工 | 新規施工と同じ設置・撤去・通知を使い、元の機体を残した追加手順と取消手順を検証。未知状態・観測外・非停止状態・完成図不一致を拒否 |
| 3 | 公開MCPと操作履歴へ接続 | `new_placement(revision_id)` → `show_operation` → `invoke_operation` → 条件付き `undo_operation`。全領域の前後を段階ごとに読戻し、書込み前に意図を保存。失敗・中断を再実行可能にしない |
| 4 | 観測した機体の有限飛行を検証 | テンプレートの合格を流用せず、起動条件・停止条件・運搬部品・到着図を明示して共通物理実行で検証 |
| 5 | サトウキビのブロック処理 | 破壊、支持を失った上部の除去、根元の成立条件を共通機構で扱い、既存作物の挙動を維持 |
| 6 | 診断の範囲を明確化 | 静的接続に関する所見と、機体・収穫の動作検証結果を区別。未対応を故障や合格へ読み替えない |

エンティティ、アイテム回収、自然成長、流体シミュレーション、サバイバル自動建築は保留。
別の作業を先に行うほうがユーザーの意図に適うと判断した場合は、その作業に着手せず
作業全体を停止し、根拠と具体案を報告する。宣言済みの差分施工は承認済み。

## 境界

- 作業領域は新しい観測として取得する。既存Revisionの範囲を未観測の空気で拡張しない。
- 初期モデルのキューは空と仮定する。静止した複数サンプルも隠れた予約や過去の履歴を証明しない。
- 差分施工は、完全なnative状態と共通物理モデルによる段階的施工の検査。
  飛行や収穫の型への適合、Blueprintの採用、所有権を自動的に確定しない。
- 保存された操作履歴から実行能力を復元しない。再起動後は履歴を読み、改めて観測・計画する。
- 条件付き取消は、施工後の全領域が一致する場合だけ可能。失敗後の自動取消・再試行はしない。
- 既存の採用・子の参照・配置済みAssemblyの期待値を、部分改造に合わせて自動変更しない。
- 公開MCP内部のコマンド施工と、通常の設置パケットによるサバイバル建築は別の入力経路。

## 現在の進捗

- 空気を明示する観測と省略する観測の集計差を修正済み。関連テスト4件合格。
- 差分施工のモデルを実装。今回の機体へのバー追加・取消、観測範囲外と不完全状態の拒否、
  観測面の変更による起動を完成図一致として受理しないことをテスト3件で確認。
- 作業領域の公開観測、MCP差分施工、共有の段階実行と保存記録を接続済み。
  ロードマップ1〜3のコードを実装し、MCP経由の追加・取消、周辺差分の拒否、
  読戻し失敗での停止、再起動後の履歴、読取り専用ポリシーを模擬transportで確認。
- 承認された固定環境と遅延支持の基盤を実装。ロードマップ4〜6も接続済み。
  観測した6ブロックの機体と2ブロックのバーを、既存の `SingleOperation` 型で
  4ブロックの片道飛行・4列の上部破壊・根元残存として検証する。
  生成テンプレートを経由せず、公開Blueprintの取り込み・提案・再起動後の再検証・採用を使う。
- 静的な方向別接続図だけではピストンの給電・準接続・飛行の故障を確定しない。
  診断の未対応と動作要件の検証を分け、動作試験を行っていない報告にはその範囲を明示。
- 公開MCPによる実機配置と収穫動作は未検証。今回、実世界は変更しておらず、
  稼働中のMCPバイナリへもまだ反映していない。

## 公開ツールの経路

```text
get_world({region: {min, max}, include_block_list: true})
  → test_circuit_change({circuit_id, changes: [...]})
  → new_placement({revision_id})
  → show_operation({operation_id})
  → 人間が具体的な案を確認
  → invoke_operation({operation_id, confirm: true})
  → get_operation({operation_id})
  → 必要な場合だけ undo_operation({operation_id, confirm: true})
```

領域は追加先の空気と停止中の機体を含め、プレイヤーの視線対象も含む。
計画は累積Revision差分と1ブロックの外周を再取得し、元の観測と照合する。
変更位置は1〜64、非空気ブロックは4096以下で、さらに配置数・領域のポリシー上限が適用される。
計画・プレビュー・実行前は、20 tickのbridge待機を挟んだ2回の完全・静止した観測を照合する。
この観測は予約イベントが存在しない証明ではない。

適用・取消の書込み前に操作記録を保存し、各実行グループの前後で全領域を読戻す。
内部モデルでコマンド処理後に予約が残らない連続工程は、順序を保って最大32個まで
まとめて書き込む。予約が残る工程は個別に待機・確認する。
プレビューの `execution_batches` / `undo_execution_batches` に実際の確認境界を表示する。
グループ内の途中状態はモデルで検査し、実機ではグループ末尾が一致した場合だけ
その範囲を検証済みとする。途中失敗では適用済みの一部があっても検証済みに昇格しない。
条件と計測範囲は [配置のまとめ処理](construction-batching.md) を参照。
失敗した試行は `needs_inspection` になり、同じ操作の再適用や自動取消を行わない。
履歴は `dustroute.world-edit.v1` として保存され、再起動後も `get_operation` で読める。
計画は実行前5分で失効し、再起動後には復元しない。

## 対象版で確認した支持挙動

対象版のローカルclassを `javap -p -c net.minecraft.block.SugarCaneBlock` で確認した。
Minecraft 1.21.11、Yarn `1.21.11+build.6` のnamed jarで、classのSHA-256は
`eb6b4a6e808b9cc8eca588e8f6ad5f1848aee5244a5148e95440dc7e71da2725`。
登録時のピストン反応は `DESTROY`。実装から確認できた支持条件は以下。

- 下が同じサトウキビなら成立する。
- 根元では下が `minecraft:dirt` または `minecraft:sand` のブロックタグに属し、
  その下ブロックの水平隣接に水のfluid tagまたは `frosted_ice` が必要。
- 形状更新時に不成立なら、1 game tick後のblock tickを予約する。
  予約時に即座には削除せず、実行時に再判定して不成立なら破壊する。
- `age=0..15` は自然成長の状態。自然成長を今回のモデルから外しても、
  実機の生育による状態変化を、構成の故障や合格へ自動変換しない扱いが必要。

これらは対象版の実装調査であり、新しい実機比較証拠ではない。
従来の隣接1面・即時除去の規則だけでは表現できないため、一度停止して基盤改修を提案し、
ユーザー承認後に下記を実装した。

## 共通の宣言と実行

- `physical::native_state::NativeState` はプロパティなし、固定値、上限付き整数を宣言。
  欠落・余分なプロパティ・非正規な整数を受理せず、状態を補完しない。
- `physical::environment::EnvironmentSpec` は native identity と物理形状、環境の役割を宣言。
  土は `dirt` / `coarse_dirt` / `rooted_dirt` の3種類。水は `water[level=0]` のみ。
  水の下と水平4面が、既知の全立方体の障壁か同じ静的水源で閉じていることを要求する。
  半ブロック・階段など部分形状の支持面だけを水の障壁として扱わない。
- `physical::lifetime::{SupportQuery, DelayedSupport}` は相対位置の同一identity・環境タグと
  AND/ORを組み合わせる。ローカルな既知空間を読み、未知位置を空気として補完しない。
  宣言した時刻・優先度・block identity guardで、既存のblock tickキューへ再判定を予約する。
- `physical::plants::PlantSpec` に `sugar_cane[age=0..15]` を宣言。
  ピストンの移動先で破壊し、上部は支持喪失の1 tick後に再判定する。
  予約後の支持復旧は保存し、別ブロックに置き換えた位置を古い予約で削除しない。
  遅延予約はcheckpoint・挙動探索の状態・型の採用検証に保持される。

初期状態には有効な支持を要求し、過渡状態の支持喪失はキューで扱う。
コマンドで植物を追加する際も、挿入前に既知の支持を要求する。
各変更後も水の境界を検査し、水源の変更・撤去や容器を開く操作はcommit前に拒否する。
水を導体・支持面・ガラスへ置換しない。土、水、各サトウキビのageをnative状態のまま保存・出力する。
一般の静的配置検証が水・植物に対応したとは扱わず、対応範囲は共通callback runtimeで検証する。

新規実行・探索は **v19**、物理受理定義は **v10**、root comparisonは **v4**。
旧v18の実行・探索コンテキストを読み替えず、新しい初期条件で再検証する。
保存済みの操作履歴は当時のプロファイル付きで参照できるが、異なる版から取消の実行能力を復元しない。
過去の実機証拠は当時の版のまま保持する。

## 観測した機体による有限収穫の要件

基準位置は元の機体の `(101,101,104)` をローカル `(0,0,0)` とした。
機体・バー8個の配置は会話中の観測を基にする。起動レバー、レバーの支持ブロック、
停止用黒曜石、4列の土・閉じた水・3段のサトウキビは**提案した初期条件**であり、
現在の実世界で取得した観測として扱わない。

レバーを操作した1回の起動に対し、機体・バー8個が東へ4進み、全ピストンが収納、
上部2段が消え、根元4個・土・水・障壁が残る到着図を独立に宣言した。
モデルではtick 1のworld tick後に入力を適用し、tick 45までにキューが空になる。
この45 tickはモデルの試験結果で、型の数値タイミング保証ではない。
`SingleOperation` の場所・kind・ピストン状態の要件に加え、別の回帰テストで全領域の
native identity・全プロパティと独立に宣言した到着図を照合する。
kindの型述語だけでサトウキビ・スライム・ガラスを識別できるとは主張しない。
根元・土・水・障壁には既存の `BlockPattern` 型も指定し、全実行状態でnative状態を保持する。

実行中のcheckpointと挙動探索状態からの再開も同じ到着図になる。
停止用ブロックが手前にある、保持を約束した根元が欠ける・ageが異なる場合は採用できない。
静的診断だけでこの飛行・収穫型へ適合すると扱わない。

## 残る実機確認と範囲外

- 新しいMCPバイナリの反映、現在の機体と農場を含む新規観測、具体的な差分案と人間の確認、
  通常MCPの施工・読戻し・取消、実機の入力時刻と収穫到着図の比較は未実施。
- 水路の造成・撤去や一般流体の挙動は未対応。ここでの水は観測済み固定環境であり、
  農場全体を空気から新規施工・全撤去できるようにした変更ではない。
- 砂、草ブロック、泥、frosted ice、水没部品や流れる水を根元の支持として追加していない。
  対象版で認められる全土・全fluid stateの実装とはしない。
- 自然成長・流体・気候変化・エンティティ・アイテム回収は未実装。
  生育などの外部変化でnative状態が変われば、読戻しの不一致として停止する。
- 生成APIの `harvest_targets.crop` は引き続きカボチャ・スイカ。
  今回の機体・畑は明示したAssemblyと汎用Blueprint更新経路で扱い、新しいエンジンpresetを足さない。
