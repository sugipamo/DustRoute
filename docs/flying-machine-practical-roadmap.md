# エンティティを除くフライングマシンの実用化

> Historical capture instructions: Mineflayer and its executable harnesses were
> removed on 2026-10-03. Commands below describe the retained trials and are no
> longer runnable in this checkout. Source is retained in Git at `9b62dcf`.
> Use [native setup](../crates/dustroute-mcp/SETUP.md) for the current backend.


基点 `9c12c96`。対象はブロック運搬、農場のブロック処理、サバイバル建築。
プレイヤーやアイテムの運動・輸送・回収は、安定後の別作業とする。

## 進める順序

1. ブロック運搬: 既存の機体・追加ブロック・到着図・採用・配置・診断を共通基盤として使う。
   材質ごとの付着、押出し上限、全部品の到着と撤去の確認を維持する。
2. 農場のブロック処理: まず成熟済みのカボチャ・スイカに対するピストン破壊を扱う。
   移動先の破壊対象の収集、破壊と移動の書込み順、通知を共通runtimeへ接続する。
   アイテム数や回収率、成長速度の保証にはしない。自然成長・水流・耕作は別途範囲を定める。
3. サバイバル建築: 資材を用意した状態からの建築を最初の候補とし、資材・参照面・
   向き・設置順・到達条件を確認する。採掘・クラフトや自律移動を暗黙に追加しない。

初回の農場対象は、確認質問で推奨した成熟済みカボチャ・スイカとした。
サバイバル自動建築は下記の前提を調査・具体案として整理した後、ユーザー判断で保留。
現在は [共同試作のアーキテクチャ整理](coauthoring-architecture.md) を優先する。

## 調査で確認した境界

- ブロック運搬は2エンジンの有限片道飛行として実装済み。往復や繰り返し操作は未検証。
- 調査時の `adhesion.rs` は進路上の `Destroy` を拒否していた。
  今回、側面の非接着判定と区別して受理済みの受動ブロックの破壊を追加した。
- 対象版の保存済み `PistonBlock` / `Blocks` 調査から、成熟したカボチャ・スイカの
  `DESTROY` と、破壊対象を書き換えた後に移動し、最後に通知する処理を確認した。
- `placePhysicalBlocks` は通常の設置パケットを使うが、クリエイティブ化、資材付与、
  テレポートを行う。現在の処理をサバイバル対応とは呼ばない。
- 共通Assembly配置はコマンド設置を検証しており、オブザーバーの明示的初期化も使う。
  手置きは設置時挙動を別途照合する必要があり、既存の合格を流用しない。
- サーバー確認読戻しはコマンド権限を使う。非OP環境まで要求する場合は、観測経路の
  変更が先に必要になるため、その実装前に報告する。

## 停止条件

エンティティ、未宣言の自然成長・流体・資材調達などを先に実装する必要が判明した場合は、
着手前に停止し、必要性と具体的な変更案をユーザーへ報告する。
既存と同じく、観測不足・予算切れ・未対応機構を成功として扱わない。

## 実装した収穫範囲

以下はv18での実装と実機証拠の記録。現在はv19でこの範囲を維持し、
[サトウキビ・固定環境・既存機体の改造](existing-machine-modification.md)も接続している。
サトウキビについてはモデル・公開MCPの回帰までで、新しい実機比較はまだ行っていない。

共通runtime v18、物理受理定義 v9。Rust の受動ブロック表へ `pumpkin` / `melon` の
`Destroy` を登録した。破壊対象は移動対象と別に収集し、12ブロックの移動数に含めない。
移動先でだけ破壊し、粘着の側面・後方の作物や、引き戻しの直接対象は破壊しない。
枝のどこかが動けない場合は、収集済みの作物も破壊しない。
対象版の順序に従い、破壊→移動先書込み→移動元処理→破壊対象と移動元の通知を実行する。
能動部品の直接破壊は、撤去コールバックがこの経路では未対応なので引き続き拒否する。

生成要求に `harvest_targets: [{ position, crop }]` を追加した。
`crop` は `pumpkin` / `melon`、位置は追加部品と同じ回転・鏡像前の座標。
初期の作物は配置図に含めるが、独立に宣言した到着図から除外する。
`destroyed_positions` は回転・鏡像後の対象位置を返す。最終的にはその位置に
機体の部品が到着する場合もあるため、単に「全対象位置が空気」では判定しない。
未収穫の作物、部品の脱落、過負荷、座標衝突を合格にしない。
対象は最大128個、距離1..16、観測位置最大512個という有限試験のまま。

[実行要求例](../crates/dustroute-translate/tests/fixtures/flying-machine-harvest-request.json)は、
スライム機に2ブロックの刃を付け、交互に並ぶ4個の作物を処理する。
生成後は通常どおり取り込み→更新提案→新しい採用→配置先の再検証→プレビュー→配置を行う。
収穫対象を含めた試験用配置であり、既存農場の成長した作物を自動探索する機能ではない。
到着後の診断と撤去も通常のAssembly経路を使用する。

v17 の保存された実行・探索コンテキストを v18 と読み替えない。
新しいnamespace・Revision・初期条件で再生成・再検証する。旧checkpointの変換は行わない。

## 検証

[証拠一覧](evidence/flying-machine-harvest-20260929.json)と
[公開MCP・読戻し・保存・サーバー記録](evidence/flying-machine-harvest-20260929.observations.json.gz)
を保持する。エンティティ物理・生成アイテム数・回収は比較対象に含めない。

- 共通runtimeの回帰では、6方向、移動上限、側面非接着、障害物による全体取消し、
  引き戻し、2個の破壊の間からのcheckpoint再開を確認した。
- 既存運搬機48構成と収穫機8構成（4方向×鏡像有無）がモデル検証に合格。
  収穫機の距離は4。他の全距離・全エンジンとの直積を検証した意味ではない。
- 枝分かれとオブザーバー、12ブロック移動、上向き破壊の3例を隔離実機と比較。
  宣言したtick末状態、書込み、予約、能動通知に不一致はなく、途中復元も一致した。
  元のサーバー記録を `tests/fixtures/device-circuits/harvest-*.json.gz` に保持する。
- 公開MCPで収穫機を再生成・取り込み・提案・採用し、(323000,180,1000) にR90配置。
  移動部品8個が南へ4進み、作物4個を破壊したnative到着図と全領域読戻しが一致。
  配置15段階・到着後の撤去11段階を確認し、MCPを5回再起動して診断・記録を再利用した。
  古い初期位置による撤去は拒否し、観測入力から得た到着状態による撤去だけが成功した。
- 各実機試験後、対象領域の空気、強制ロード解除、サーバー正常停止を確認した。
- 関連Rustテスト56件、保持した実機観測の再比較を含むPythonテスト14件、
  workspace全targetのClippy、fmt、実機ハーネスのJavaScript構文確認が合格。

再実行する場合は新しいnamespace・run-id・空き座標を使う:

```sh
target/debug/examples/generate_flying_machine request.json > .local/harvest.fixture.json
python3 tools/observe_assembly_construction.py --run-id harvest-next --x 324000 --fixture .local/harvest.fixture.json --rotation r90 --persistence --capture-construction
```

## サバイバル建築で先に必要な機構

通常の設置には、クリックする既存ブロックの面と届く作業位置が必要になる。
現在の空中コースは対象領域が空気であることを前提としており、最初のブロックや
離れた停止装置を手置きするための仮設参照面を宣言していない。
足場を置きっぱなしにすると粘着で機体へ取り込む可能性があり、撤去順も
オブザーバーへの通知と起動状態に影響する。単に資材を減らす配置へ置換できない。

Java 1.21.11 の `BlockItem.place` は flags=11 の書込み後に `onPlaced` を呼ぶ。
現在のコマンド配置は事前の形状処理と flags=258、その後の通知を扱う。
通常のオブザーバー設置ではコマンド用の `powered=true` 初期化を使わない。
この差を省略してコマンド設置の検証結果を通常設置の証明に流用しない。

次の実装案:

1. 共通runtimeに通常設置の入力経路を追加し、既存の書込み・通知処理を共有する。
   最初は機体の構成部品に絞り、向き・参照面・設置時状態を明示する。
2. 資材表と手持ち数を照合する。資材付与、クリエイティブ化、テレポートを行わず、
   資材不足・届かない位置・向き不一致では停止して観測結果を残す。
3. 本体・仮設物・残す環境を別々に宣言し、仮設物の撤去を含む手順を検証する。
   初回は足場とBotの作業位置を人間が指定する。自律経路探索と足場の自動生成は別範囲。
4. 隔離実機で資材消費、全工程の読戻し、部分失敗時の診断、足場撤去後の起動を確認する。

ユーザー指定の「宣言外の機能が先に必要なら停止」に従い、仮設構造の生成・撤去と
サバイバル用の通常設置経路は未着手。エンティティ物理、自然成長、アイテム回収も未着手。
