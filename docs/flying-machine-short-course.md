# 固定コースのフライングマシン比較

2026-09-28、`codex/piston-adhesion` / 基点 `0b6a0cc`。
Java 1.21.11、実行profile v17。物理runtimeを変更せず、既存の粘着移動・
可動ピストン・可動オブザーバーを組み合わせた有限距離の試験。

## 目的と手順

無人の一方向機を1種類、既知の固定空間で10ブロック自走させて停止する。
起動前の読戻し、実入力時刻、書換えとイベント、停止後の読戻しを使い、
実機から導出した状態とシミュレータを絶対座標で比較する。
追加機構や大きな改修が先に必要と判明した場合は、着手前に停止して報告する。

1. 6ブロックの機体、固定した起動レバー、黒曜石の停止装置を定義。
2. シミュレータで有限距離の停止と途中状態からの復元を確認。
3. 隔離サーバーで同じ配置・入力を計測し、元データと比較結果を保持。
4. 10ブロックの到達、部品の欠落・置き去りがないこと、停止後の静止区間を
   実機記録から別途検証。モデルと同じ誤動作でも到達成功にはしない。

## 構成

機体のブロックは以下の6個。座標は初期位置に対する相対値、向きはMinecraftの
ブロック状態。オブザーバーは上を観測し、下のスライムへ給電する。

| 座標 | ブロック | 向き |
| --- | --- | --- |
| (0, 0, 0) | スライム | — |
| (0, 0, 1) | 通常ピストン | 東 |
| (0, 1, 0) | オブザーバー | 上 |
| (1, 0, 0) | 粘着ピストン | 西 |
| (1, 0, 1) | スライム | — |
| (1, 1, 1) | オブザーバー | 上 |

固定レバーは (0, 2, 0)、支持する石は (-1, 2, 0)。レバーOFF→ONを一度だけ入力する。
(12, 0, 1) の黒曜石が前進を止め、機体6個は元の形で +X に10移動する。
オブザーバーを機体の残りより先に設置し、設置パルスが機体へ伝わらない順序にする。
100クライアントtickの待機に加え、起動前の全領域読戻しで初期状態を検査する。
クライアントの待機時間をサーバーの実入力時刻へ置き換えて使わない。

領域は (-4, -3, -3)〜(15, 5, 4) の1,440セル。経路、停止装置、周辺の空気を含む。
試験原点は (260000, 180, 1000)。領域の空きと対象版・feature flagsを確認してから配置した。
連続した領域内の変更を記録し、追従窓は導入しない。

## 結果

[証拠一覧](evidence/flying-machine-20260928.json)と
[独立した実機記録](../crates/dustroute-translate/tests/fixtures/device-circuits/flying-short-course.json.gz)
を保持する。

- 1回の実入力で10ブロック前進。0〜10の各移動量で、6個すべてが元の形・状態に
  戻ったフレームを確認した。途中のフレームが静止して見えても、予約イベントの不在は意味しない。
- 171 tick終端の全領域、313書込み、42部品tick配送、1,066有効部品への通常通知と、
  ピストンイベント・carrier境界の宣言した比較範囲で一致した。
- 最後の書換えは相対tick105。比較終端171まで66tickの書換え・部品tick配送なし。
  サーバー確認済みの最終読戻しも同じ状態で、機体の欠落・残骸はない。
- シミュレータは予約0で完了し、正確なcheckpoint・探索用の途中状態からの復元も一致した。
- 試験領域を撤去して全セル空気を確認し、強制ロードを解除、サーバーを正常停止した。
- Pythonテスト37件が合格。今回を含む55件の保存済み実機記録を現在のモデルで
  再生し、復元も検証した。Rust実装の変更・再ビルドは行っていない。

`flying_machine_trial.flight_progress` は相対移動量と機体形状を診断する。
物理の実行や実機との比較を相対座標へ置き換えず、元の絶対座標・通知順を保持する。
共有比較器は入力時刻の未確認・連続ログの欠落・読戻し不一致を合格にしない。
追加の到達検査は、部品の欠落、残骸、静止区間不足を拒否する。

## 再現

既存の隔離計測サーバーと比較用exampleを使う。既存のrun-idと出力を上書きしない。

```sh
python3 tools/flying_machine_trial.py --output .local/flying-next.fixture.json
python3 tools/observe_device_circuit.py --fixture .local/flying-next.fixture.json --run-id flying-next --x 270000
python3 -m unittest discover -s tools -p 'test_*.py'
```

原点の変更は新しい比較試験になる。モデル出力を実機の期待値として保存しない。

## 今回の境界と次の課題

この機体・座標・10ブロックの走行についての比較であり、無限走行、任意座標・方向、
チャンクの読込解除、荷物やプレイヤーの運搬、故障からの再起動は保証しない。
実機の隠れた全予約・履歴と、全形状通知を観測したという主張も含まない。

公開MCPでのフライングマシン用の型・採用・配置・移動後の診断と撤去は今回未実施。
現在の固定位置・静止状態を前提にした契約へ、有限走行の到達条件をどう接続するかは
次の作業で扱う。今回、物理runtime・追従観測・補助MODの追加改修は必要なかった。
